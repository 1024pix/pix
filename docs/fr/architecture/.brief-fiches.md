## Le fil d'exemple commun : `Organization`

Les fiches Entity et Aggregate Root utilisent `Organization`. Les fiches des couches suivantes
continuent ce fil, pour qu'un junior suive la même organisation de la route jusqu'à la base. Reprends
exactement ces noms et signatures (TypeScript) quand ta fiche s'y prête :

- **Domaine** : `Organization<Id extends OrganizationId | null = OrganizationId>` ;
  `Organization.create({ name, type, createdBy, now }): Organization<null>` ; `rename(name, now)`,
  `archive(now)`, `enableFeature(featureName, params, now)` ; `isManagingStudents` ; `createdBy: UserId` ;
  `OrganizationFeature` (objet interne) ; erreurs `ArchivedOrganizationError`,
  `FeatureAlreadyEnabledError`, `InvalidOrganizationError` (des `DomainError`).
  Vraie règle du code : si `LEARNER_IMPORT` est activée, `isManagingStudents` est toujours `false`.
- **Repository** : port `OrganizationRepository { get(id): Promise<Organization>; add(organization:
  Organization<null>): Promise<Organization>; update(organization: Organization): Promise<void> }`.
  Implémentation dans `organizational-entities/infrastructure/repositories/organization-repository.ts`,
  connexion par `DomainTransaction.getConnection()`, tables `organizations` et `organization-features`,
  fonctions locales `toDomain(row)` et `toRow(organization)`.
- **Usecases** : `createOrganization({ organization, organizationRepository })` reçoit une
  `Organization<null>` ; `archiveOrganization({ organizationId, organizationRepository, clock })` ;
  `enableOrganizationFeature({ organizationId, featureName, params, organizationRepository, clock })`.
  Un usecase ne modifie qu'un Aggregate.
- **Contrôleur** : `create(request, h)` lit `createdBy` (utilisateur connecté), demande au sérialiseur
  de désérialiser le payload en `Organization<null>`, appelle `usecases.createOrganization({ organization })`,
  renvoie `h.response(organizationSerializer.serialize(organization)).created()`.
- **Sérialiseur** : `deserialize(payload, { createdBy, now }): Organization<null>` (traduit le JSON puis
  appelle `Organization.create`, aucune règle métier, aucune validation de forme) ;
  `serialize(organization: Organization)` produit le JSON:API.
- **Route** : `POST /api/admin/organizations`, forme du payload validée par Joi dans la route, contrôle
  d'accès en pre-handler, handler = le contrôleur.
- **API interne** : `organizationApi.getOrganization(id): Promise<OrganizationDTO>` avec
  `OrganizationDTO { id, name, type, isRestricted, isArchived }`. `isRestricted` =
  `isManagingStudents` ou `LEARNER_IMPORT` active, calculé par organizational-entities. Un autre contexte
  lit cette API par un repository à lui (Anticorruption Layer), jamais directement depuis un usecase.
- **Read-model** : un objet assemblé seulement pour l'affichage, par exemple la liste des organisations
  de Pix Admin. Il ne porte aucune règle.

Si ta fiche ne se prête pas au fil (Specification, Domain Service peut-être), choisis un autre exemple
d'après le vrai code, et vérifie dans le code la vraie règle du métier qui le justifie. Dis-le dans le
rapport.

## Règles à ne pas oublier (résumé du gabarit)

- Partie à consulter : définition, « Les règles » (phrase + tableau), « Exemple complet » qui couvre
  TOUTES les règles avec un commentaire `X1 : …` par règle, « Comment tester » (liste avec « Exemple :
  `nom du test` », puis le code du test, qui se lit seul), « Checklist de revue de code » (groupée par
  questions courtes).
- Référence : pour chaque règle, La règle / Bon exemple (extrait de l'exemple complet) / Mauvais
  exemple (le même code mal écrit) / Ce que ça apporte / Sans cette règle (un bug concret, sur
  l'exemple) / À savoir et Exceptions (facultatifs).
- Exemples en TypeScript, un seul fil, « Exemple inventé, d'après [`fichier.js`](permalien) ».
- Interdits : date, état du code, historique, citation d'ADR, renvoi aux documents de travail
  (`explication.md`, `outillage.md`, `ecarts.md`), lien vers un fichier de Pix qui fait la faute,
  question ouverte, section vocabulaire, question de tri, mot « double », événements du domaine (mis de
  côté).
- Langue : français parlé d'un dev qui explique à un collègue. Phrases courtes. « On » permis, pas de
  « je ». « getter » plutôt qu'« accesseur ». Pas de mots vagues (propre, clair, simple, sans risque,
  protéger, frontière, robuste). Pas de paires de phrases symétriques ni de slogans. Pas de deux-points
  en cascade. Noms DDD en anglais.
- Liens vers une autre fiche : `../<dossier>/README.md`, à la première apparition du terme.
